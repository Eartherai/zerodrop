ZeroDrop: evidence

The migration agent that proves nothing was lost. This page is EVIDENCE.md from the repository, with the key Neatlogs captures on top. Every number comes from a saved result file.

One page that maps what the neatHack rules ask for to a file, a run id or a trace in this repository. Every number here is copied from a saved result file; nothing is estimated. Where something is missing or weak, it says so.

The result rows in section 7 and the totals (seven false successes, 182 and 28 records, $4.06) are recomputed from those files on every push by the ci workflow (scripts/verify_numbers.py); it fails if a number here stops matching a file. The same workflow runs the tests and three runs of the agent with scripted planners (no model, no keys).

What Neatlogs got right and wrong (full notes in evidence/neatlogs/investigation-report.md):

  • Right: the five evidence traces on the critical incident are exactly our recorded real-model false successes, covering all three causes. Its count of ten comes from a search for "False Success Claim: true".
  • We did not take its first recommendation (move the verifier's checks into the agent's dry run): that would end the verifier's independence. We took its fourth step, a blocking check that asks the evaluator.
  • Wrong: the follow-up investigation cites three healthy runs as examples, and the repair-loop incident's evidence traces are successful one-replan recoveries. The run that really looped is trace a5b9ad484e4fac9e428f5eb00ba46088.
  • Honest timing: fixes 1 to 6 were made before the board had an incident on it. Fix 7 and the halt message are the two changes that came from the incidents.

4. Neatlogs tracing

Rules: traces "should capture model and tool calls, state changes, retries, failures, latency, token usage, and cost".

Asked for Where it is in a ZeroDrop trace Code
Model calls, tokens, cost, latency LLM spans from the wrapped model client, under AGENT spans for the planner and the diagnoser src/zerodrop/agent/
Tool calls TOOL spans for schema discovery, every batch write (novabill.batch_write, with attempt number), every lookup, and every tool the model calls, with its input and result src/zerodrop/engine.py, src/zerodrop/agent/llm.py
State changes One state.<STATUS> span per run status change, with from_state and to_state MigrationEngine._set_status
Retries and failures One recovery.<class> span per failure handled: transient (wait and retry), ambiguous write (look up first), contract change (replan), bad data (quarantine), auth, budget (halt) src/zerodrop/engine.py
The gates before and during writing GUARDRAIL spans: one per dry run (dry-run.<entity>) and one per early check (early-check.<entity>), each with what was checked, passed or not, a score, and the reason when it blocks MigrationEngine._guarded_dry_run, _check_early
The verdict Root WORKFLOW span: verifier status, the agent's own claim, false-success flag, checks failed, report hash. EVALUATOR span for the verifier with its input, verdict and a score MigrationEngine._finish, _verify

Every run stores its trace id in the ledger; the dashboard links to it. Layer: src/zerodrop/telemetry.py. What Neatlogs itself showed for the project on the morning of Oct 12 (read off its project overview; no file was saved): 225 traces in seven days, a 28.4% trace error rate and $2.56 of measured model spend. The error rate counts runs with any errored span, and our scenarios inject faults on purpose, so it is not the agent's failure rate.

Reading it honestly:

  • Seven real false success claims in total. The verifier caught all seven. Each of the three causes was fixed test first, and no later run repeated a fixed cause.
  • Three full passes of all 20 scenarios in a row matched with no false success, the last one on the final code. On the final code, gemini-3.1-flash-lite, the model that produced all seven false successes, also matched 18 of 18 with none.
  • Pass 3 also had one run the model never repaired (S12) and one halted by a provider 503. Both led to changes (fix 6, the 503 retry). When we later seeded the same wrong mapping and let real models repair it, both gemini-3.5-flash-lite and gemini-3.1-flash-lite repaired it at the first attempt with the guard off and on (evidence/experiments/), so fix 6 is shown harmless and seen working inside one repair conversation, but not shown rescuing a run.
  • Pass 4 and the morning pass after fix 7 were cut short when the free tier's daily quota ran out. Scenarios stopped by the quota are counted as not run; two of them had already made model calls and wrote no records.
  • One pass per commit. This shows what happened, not a failure rate.
  • All real-model runs used Gemini Flash models on the free tier (nothing was charged). No Claude run exists: the Anthropic account had no credit during the hackathon.

Real-model cost of every saved run: $4.06 at list price, $0 charged (free tier).

Files: evidence/eval/ (one JSON and one Markdown per evaluation), evidence/runs/ (one JSON per single run), evidence/experiments/. Reproduce the scripted ones with no keys: uv run zerodrop eval --planner oracle --label my-run.
