# ZeroDrop evaluation

## Method
- **20 seeded scenarios** (`scenarios/scenarios.yaml`): clean runs at three sizes, rate-limit storms, 5xx bursts, timeout after a committed write, partial batch acceptance, breaking API changes (v1 to v2) at two points, process crashes with resume, orphan and duplicate records, credential rotation and revocation, prompt injection in source data, slow and flaky APIs, and two combined-chaos runs.
- Each scenario starts fresh sandbox services with its own seeded fault plan, which the agent never sees, and ends with the **independent verifier**: counts, duplicates, money per currency in exact minor units, referential integrity, quarantine accounting, and a field-by-field comparison with golden records generated alongside the data.
- **Expected outcome** = what the verifier should report for a correct agent: SUCCESS, PARTIAL_SUCCESS (orphans and duplicates must be quarantined and reported), or WAITING_FOR_APPROVAL (revoked credentials with no replacement).
- **False success claim** = the engine believed SUCCESS but the verifier disagreed.
- Reproduce: `uv run zerodrop eval --planner oracle --label <name>` writes JSON + Markdown to `evidence/eval/`; compare with `uv run python scripts/compare_evals.py <a.json> <b.json> ...`.

## What these runs measure (and what they do not)
Two kinds of runs are reported here, and they answer different questions.
- **Real-model runs** (Gemini planner, next section): a real model reads both schemas and writes the mapping. These measure the whole agent. One pass per commit, so they show what happened, not a failure rate.
- **Oracle-planner runs** (last section): a deterministic, scripted stand-in that always proposes the correct mapping. They measure everything around the model: engine, recovery policies, crash/resume, the sandbox and the verifier. They cost nothing and are exactly repeatable. They do not measure a model's mapping quality.

No run used Claude: the Anthropic account had no credit during the hackathon. The planner sits behind one interface (`LLMBackend`), so the model is a setting.

The **naive planner** (a scripted, plausible but flawed agent) shows what the verifier is for. It reads source dates in the wrong time zone. On S01 the engine believes SUCCESS and the verifier reports FAILED: every customer's `created_at` is off by five and a half hours (`tests/test_runner_api.py::test_naive_planner_is_caught_by_the_verifier`). Until Oct 11 its flaw was two decimals for every currency (yen 100x too large); fix 5 below made the engine reject that mapping before any write, so the scripted flaw had to change to one the engine cannot know about.

### Improvement 3: a real model's false success, caught and then prevented (commit 251cdd4)
- **Observed:** with the smallest model (`gemini-3.1-flash-lite`, commit `78d92da`) five of eight
  runs ended with the engine believing SUCCESS while the verifier reported FAILED: one record per
  entity on the target instead of hundreds. These are real false success claims, and the
  independent verifier caught every one.
- **Root cause:** the model mapped `external_id` with a constant (`const "C000001"`) instead of
  the source id. Every payload was valid on its own, so the dry run passed all samples. The
  target then treated each write as a record it already had, and the engine counted them as done
  (1,898 "already present" out of 1,901 in the S02 run, `run_5d0171f3cddf`).
- **Fix (test first):** the dry run now rejects a mapping that gives different source records
  the same identity (`duplicate_identity`) and hands it back to the model to repair before any
  write. Regression tests use the exact mapping the model produced.
- **Result:** the same five scenarios, same model, at the fix commit: five of five verified
  SUCCESS, zero false success claims. In S20 the guard visibly triggered one repair. In the other
  four the engine-side repair counter is zero, so either the model's own dry-run tool call caught
  it during planning or the model did not repeat the mistake. One run each: this shows the guard
  works when the mistake happens, not how often the mistake happens.
- Scripted evaluation at the fix commit: 18 of 18 matched (large-scale scenarios excluded),
  `evidence/eval/*after-fix3-identity-guard.md`.

### Improvement 4: contradictory amount parameters (commit 933a7a9)
- **Observed (pass 2, S16, `run_14ded6031abe`, trace `874c2d43e3b1995e85980d50264aed3f`):** the
  engine believed SUCCESS; the verifier reported FAILED on three checks. JPY total on the target
  1,205,966,500, expected 12,059,665: exactly 100 times too large, on 157 invoices.
- **Root cause:** after the API change the model rewrote the invoice mapping and gave
  `decimal_to_minor` both `decimals: 2` and `currency_field`. The mapping language silently used
  the fixed value. Yen has no minor unit, so every yen amount was multiplied by 100. Every
  payload was valid, so the dry run passed.
- **Fix (test first):** when both parameters are given and they disagree for the record's
  currency, the operation is a mapping error. The dry run returns it to the model to repair.
- **Result:** scripted regression 18 of 18 (`*after-fix4-currency-params.md`). In pass 3, S16
  on the same model was verified SUCCESS (`run_e5294505e55c`).

### Improvement 5: fixed decimals against the record's own currency (commit 7b34f8c)
- **Observed (pass 3, S03, `run_acc170ca8785`, trace `81e79b05a4b1b6f2c15dbd833823ef1f`):** the
  same symptom by a different route. JPY total 328,713,000, expected 3,287,130, on 24 invoices.
  This time the model gave only `decimals: 2`, so fix 4 had nothing to compare.
- **Root cause:** a fixed number of decimals is only right when every record has a currency
  with that many. The record itself says which currency it is.
- **Fix (test first):** if a record carries a known currency code whose minor units differ
  from the fixed `decimals`, the operation is a mapping error that names `currency_field` as
  the repair.
- **Result:** scripted regression 18 of 18 (`*after-fix5-currency-guard.md`). In pass 4, S03 on
  the same model was verified SUCCESS (`run_30e7764a777f`), as were the other nine scenarios
  that ran.
- **Side effect:** the scripted naive planner used this exact flaw to demonstrate a false
  success. The engine now rejects it, so the naive planner's flaw was changed to a wrong time
  zone, which only the verifier's field comparison can see.

### Improvement 6: never send again what the target already refused (Oct 12)
- **Observed:** the S12 run above. Not a false success, but the engine sent the same refused
  plan values three times, because each repair passed the dry run.
- **Root cause:** the dry run checks a payload's shape against the schema. It cannot know that
  a reference points at nothing. After the target says so, the engine knows, but it forgot.
- **Fix (test first):** when the target refuses reference values across a batch, the engine
  remembers them for that entity and field until the target's version changes. A dry run then
  fails a mapping that still produces those values on most samples (`refused_reference`). The
  model's own dry-run tool and the submission check use the same dry run, so the model is told
  inside the repair conversation, before anything is written. Refused values on only a few
  records are left alone: those are record problems and are quarantined as before.
- **Tests:** `tests/test_engine.py`, four tests, starting from the exact mapping the model
  wrote. A repair that keeps the refused values no longer reaches the target a second time.
- **Checked with a real model, and what that check does not show:**
  `scripts/repro_refused_reference.py` seeds the model's wrong mapping and lets a real model do
  the repairs. On `gemini-3.5-flash-lite`, with the guard off (`run_f5f2c8dc4a2c`) and on
  (`run_29dc26ee4a25`), the model repaired at the first attempt and both runs were verified
  SUCCESS. So the guard does no harm there, and this model did not need it. Two more runs with
  the guard on (`run_937b40adc42e`, `run_173c027fcabe`) were also verified SUCCESS. In the
  second, the trace shows the guard at work inside the repair conversation: the model's first
  dry-run call came back FAILED with `refused_reference` and the refused values named, and its
  next attempt passed (trace `464dab9520337ad55f0a685d5bece651`,
  `evidence/screenshots/17-…png`). What is still **not** shown: a run that fails without the
  guard and passes with it. The model that did fail, `gemini-3.1-flash-lite`, was out of daily
  quota. Files: `evidence/experiments/`. The first two runs used the working tree that became
  commit `6c07c9f` and record its parent, `1838455`; the last two record `a16cfa9` and ran on
  the tree that became the next commit.

### Improvement 7: the independent verifier re-reads the first batch (Oct 12, commit 286c728)
- **Where it came from:** the critical incident Neatlogs raised on our traces, "False Success
  Claims (Agent SUCCESS, Evaluator FAILED)". Its recommended action ended with "implement a
  blocking pre-commit validation step that queries the evaluator before claiming success"
  (`evidence/neatlogs/`).
- **Gap it closes:** fixes 3, 4 and 5 reject three specific mapping mistakes in the dry run. A
  fourth mistake the dry run cannot see would still write every record before the verifier
  said FAILED.
- **Fix (test first):** the verifier gains `spot_check`: the same field-by-field comparison as
  `verify`, for the records of one batch. The engine writes one batch spread over the whole
  entity (so it holds every currency and status, not only the oldest rows), asks the verifier
  about exactly those records, and halts if they do not match the source. It asks again when a
  mapping changes mid-run. The verifier still imports nothing from the engine, and its findings
  go into the halt message, never to the planner.
- **Before and after** (S01, scripted planner with a wrong time zone, early check off and on):
  182 records written and a false success claim (`run_352df589b91d`), against 28 records
  written and the agent reporting FAILED itself (`run_0c898a7e56b0`). Traces
  `c2fce46175145a8e7473297151bf04da` and `35bb1a754af7df0c21393e7118cd203e`.
- **No regression:** scripted suite 20 of 20 with the check on. Real model: 8 of the 8
  scenarios that ran before the daily quota ended (24 early checks, none failed), then the
  full pass below.
- **Limit:** it checks one batch per mapping version. A mistake that only shows on a record
  outside that batch is still caught only by the final verification.

### Improvement 1: rate-limit waits are not failures (commit 8c0a017)
- **Observed:** in the baseline S03 run, six consecutive 429 responses exhausted the six-attempt budget. The engine halted with 66 of 116 invoices unwritten. The verifier reported FAILED with per-currency shortfalls; the agent's own claim was FAILED, so there was no false success.
- **Root cause:** `_write` counted a 429 with Retry-After as a failed attempt.
- **Fix:** rate-limit waits get their own budget (`max_rate_limit_waits = 40`) on write and read paths; the wall-clock cap still applies.
- **Regression test:** nine consecutive 429s now end in a verified SUCCESS.
- **Result:** S03 FAILED -> SUCCESS; 19/20 -> 20/20 scenarios matched.

### Improvement 2: wait exactly what the server asks (commit 574aa2b)
- **Observed:** after fix 1, S03 still spent about 12 s waiting for six 0.2 s Retry-After hints, because the engine used max(own exponential backoff, Retry-After).
- **Fix:** with a Retry-After present, wait exactly that long (capped at 60 s); capped, jittered exponential backoff applies only when no hint is given.
- **Regression test:** six recorded waits, each within 0.20–0.25 s.
- **Result:** S03 12.1 s -> 2.8 s; S16 (demo chaos) 12.0 s -> 11.1 s; S20 6.5 s -> 5.8 s. Outcomes unchanged (20/20).
